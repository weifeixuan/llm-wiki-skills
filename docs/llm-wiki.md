# LLM Wiki

一个用 LLM 构建个人知识库的模式。

这是一份想法文件，设计上就是让你复制粘贴给自己的 LLM Agent（例如 OpenAI Codex、Claude Code、OpenCode / Pi 等等）用的。它的目标是传达高层次的思路，具体的细节由你的 agent 与你协作完成。

## 核心想法

大多数人对 LLM 和文档的体验是 RAG 式的：你上传一批文件，LLM 在查询时检索相关的片段，然后生成答案。这样可行，但 LLM 每次回答都在从零开始重新发现知识。没有积累。问一个需要综合五份文档才能回答的细微问题，LLM 每次都得重新查找并拼凑相关片段。什么都没有沉淀下来。NotebookLM、ChatGPT 的文件上传，以及大多数 RAG 系统都是这样工作的。

这里的想法不同。LLM 不只是在查询时从原始文档中检索，而是**增量地构建并维护一个持久的 wiki** —— 一组结构化、互链的 markdown 文件，介于你和原始资料之间。当你添加一份新资料时，LLM 不只是把它索引进去等着以后检索，而是阅读它、提取关键信息、把它整合进现有的 wiki —— 更新实体页面、修订主题摘要、标注新数据与旧论断的矛盾之处、加强或挑战不断演进的综合结论。知识被编译一次，然后持续*保持最新*，而不是每次查询都重新推导。

这是关键区别：**wiki 是一个持久的、复利的产物。** 交叉引用已经就位。矛盾已经被标注。综合结论已经反映了你读过的所有内容。每添加一份资料、每提出一个问题，wiki 都变得更丰富。

你从不（或极少）亲自写 wiki —— 全部由 LLM 撰写和维护。你负责选材、探索和提出正确的问题。LLM 承担所有的苦活 —— 总结、交叉引用、归档、簿记，正是这些让一个知识库能长期真正有用。实践中，我把 LLM agent 开在一边，Obsidian 开在另一边。LLM 根据我们的对话做修改，我实时浏览结果 —— 跟随链接、查看图谱视图、阅读更新后的页面。Obsidian 是 IDE，LLM 是程序员，wiki 是代码库。

这可以应用到很多不同的场景。举几个例子：

- **个人**：追踪自己的目标、健康、心理、自我提升 —— 归档日记、文章、播客笔记，逐步构建一幅关于自己的结构化图景。
- **研究**：在数周或数月里深挖一个主题 —— 读论文、文章、报告，增量地构建一个综合 wiki 和不断演进的核心论点。
- **读一本书**：边读边归档每一章，为人物、主题、情节线索以及它们之间的联系构建页面。读完时你就拥有了一个丰富的伴读 wiki。想想 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) 这类粉丝 wiki —— 数千个互链页面覆盖人物、地点、事件、语言，由志愿者社区历时多年建成。你完全可以在阅读时用 LLM 做所有的交叉引用和维护，个人就建成类似的东西。
- **商业/团队**：由 LLM 维护的内部 wiki，输入源是 Slack 讨论、会议转录、项目文档、客户通话。可以有人工审核更新环节。wiki 之所以保持最新，是因为 LLM 做了团队里没人愿意做的维护工作。
- **竞争分析、尽职调查、旅行规划、课程笔记、爱好深挖** —— 任何需要长期积累知识并希望它井然有序而非散落一地的事情。

## 架构

一共三层：

**原始资料** —— 你精选的源文档集合。文章、论文、图片、数据文件。它们是不可变的 —— LLM 从中读取但绝不修改。这是你的事实来源。

**wiki** —— 一个由 LLM 生成的 markdown 文件组成的目录。摘要、实体页面、概念页面、对比、总览、综合。这一层完全由 LLM 拥有。它创建页面、在新资料到来时更新页面、维护交叉引用、保持一切一致。你来读；LLM 来写。

**模式文件（schema）** —— 一份文档（例如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md），告诉 LLM wiki 如何组织、有哪些约定、以及在摄取资料、回答问题或维护 wiki 时要遵循什么工作流。这是关键的配置文件 —— 正是它让 LLM 成为一个有纪律的 wiki 维护者，而不是一个泛泛的聊天机器人。你会和 LLM 一起随着时间共同演进这份文件，直到它适配你的领域。

## 操作

**摄取（Ingest）。** 你把一份新资料丢进原始资料集合，然后让 LLM 处理它。一个示例流程：LLM 读取资料，与你讨论核心要点，在 wiki 中撰写摘要页，更新索引，更新 wiki 中相关的实体页和概念页，并在日志中追加一条记录。一份资料可能触及 10-15 个 wiki 页面。就我个人而言，我喜欢一次摄取一份资料并保持参与 —— 我读摘要、检查更新、引导 LLM 该强调什么。但你也可以批量摄取多份资料，少一些干预。由你决定并发展适合自己风格的工作流，并把它写进 schema 文件供后续会话参考。

**查询（Query）。** 你针对 wiki 提问。LLM 搜索相关页面、阅读它们，然后综合出带引用的答案。答案可以有多种形式，取决于问题 —— 一个 markdown 页面、一张对比表、一份幻灯片（Marp）、一张图表（matplotlib）、一块画布。重要的洞察是：**好的答案应该归档回 wiki，成为新的页面。** 你要的对比、一个分析、你发现的一个关联 —— 这些都有价值，不该消失在聊天记录里。这样，你的探索就和摄取的资料一样，在知识库里复利增长。

**体检（Lint）。** 定期让 LLM 对 wiki 做健康检查。查找：页面之间的矛盾、被新资料取代的过时论断、没有入链的孤儿页面、被提及却还没有自己页面的重要概念、缺失的交叉引用、可以通过网络搜索填补的数据缺口。LLM 很擅长建议值得研究的新问题和值得寻找的新资料。这让 wiki 在增长过程中保持健康。

## 索引与日志

两个特殊文件帮助 LLM（和你）在 wiki 变大后导航。它们 purpose 不同：

**index.md** 是面向内容的。它是 wiki 中一切内容的目录 —— 每个页面带链接、一行摘要，可选地附带日期或资料数量等元数据。按类别组织（实体、概念、来源等）。LLM 在每次摄取时更新它。回答查询时，LLM 先读索引找到相关页面，再深入阅读。在中等规模（约 100 份资料、数百个页面）下这套方法出奇地好用，并且避免了基于 embedding 的 RAG 基础设施。

**log.md** 是按时间顺序的。它是一份只追加的记录，记载发生了什么、什么时候发生的 —— 摄取、查询、体检。一个实用技巧：如果每条记录都以一致的前缀开头（例如 `## [2026-04-02] ingest | 文章标题`），这份日志就可以用简单的 unix 工具解析 —— `grep "^## \[" log.md | tail -5` 就能得到最近 5 条记录。日志给你一条 wiki 演化的时间线，也帮助 LLM 了解最近做了什么。

## 技巧与窍门

- **Obsidian Web Clipper** 是一个把网页文章转换成 markdown 的浏览器扩展。对快速把资料存进原始资料集合非常有用。
- **把图片下载到本地。** 在 Obsidian 设置 Settings → Files and links 中，把"Attachment folder path"设为固定目录（例如 `raw-原始资料/assets-附件/`）。然后在 Settings → Hotkeys 中搜索"Download"，找到"为当前文件下载附件"并绑定一个快捷键（例如 Ctrl+Shift+D）。剪藏一篇文章后按下快捷键，所有图片就会下载到本地磁盘。这一步可选但有用 —— 它让 LLM 能直接查看和引用图片，而不依赖可能失效的 URL。注意 LLM 无法在一次阅读中原生读取带内联图片的 markdown —— 变通办法是让 LLM 先读文本，再分开查看部分或全部被引用的图片以获得额外上下文。有点笨拙，但效果足够好。
- **Obsidian 的图谱视图** 是查看 wiki 形态的最佳方式 —— 什么连着什么，哪些页面是枢纽，哪些是孤儿。
- **Marp** 是基于 markdown 的幻灯片格式。Obsidian 有对应插件。适合直接从 wiki 内容生成演示文稿。
- **Dataview** 是一个对页面 frontmatter 执行查询的 Obsidian 插件。如果你的 LLM 给 wiki 页面加了 YAML frontmatter（tags、日期、资料数量），Dataview 可以生成动态表格和列表。
- wiki 就是一个装着 markdown 文件的 git 仓库。版本历史、分支和协作都是免费送的。

## 为什么这行得通

维护知识库的繁琐之处不在于阅读或思考 —— 而在于簿记。更新交叉引用、保持摘要最新、标注新数据与旧论断的矛盾、在几十个页面之间维持一致性。人们放弃 wiki，是因为维护负担的增长快于价值的增长。LLM 不会厌倦、不会忘记更新交叉引用，而且可以一次改动 15 个文件。wiki 之所以保持维护，是因为维护成本趋近于零。

人类的职责是策展资料、引导分析、提出好问题、思考这一切意味着什么。LLM 的职责是其余的一切。

这个想法在精神上与 Vannevar Bush 的 Memex（1945）一脉相承 —— 一个个人化的、精心策展的知识库，文档之间有联想式的路径。Bush 的愿景比实际的万维网更接近这里描述的东西：私有的、主动策展的、文档之间的连接和文档本身一样有价值。他没能解决的是"谁来做维护"。LLM 解决了。

## 说明

这份文档刻意保持抽象。它描述的是想法，而不是某个具体实现。确切的目录结构、schema 约定、页面格式、工具选择 —— 所有这些都取决于你的领域、你的偏好和你选择的 LLM。上面提到的一切都是可选和模块化的 —— 有用的就采用，没用的就忽略。例如：你的资料可能纯文本，那你根本不需要图片处理。你的 wiki 可能小到 index 文件就足够，不需要搜索引擎。你可能不在乎幻灯片，只想要 markdown 页面。你可能想要一套完全不同的输出格式。正确的用法是把它分享给你的 LLM agent，一起协作，实例化一个适合你需求的版本。这份文档唯一的任务就是传达这个模式。剩下的，你的 LLM 自己会搞定。
